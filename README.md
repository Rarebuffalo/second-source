# Second Source

**Every AI claim needs a second source.**

AI agents report on their own work: *"All tests pass." "Fixes #123." "Deployed to staging."*
Second Source checks those claims independently, against evidence from the systems the agent
acted on, and keeps re-checking that they stay true.

The first domain is **coding agents**. On every pull request opened by Claude Code, Codex,
Copilot, Cursor, Devin or Jules, it tells you which of the agent's claims hold up against CI
results, changed files, issue state and Git history, and it keeps watching after the merge:
did "Fixes #123" really close the issue, and is it still closed a month later? Was the change
reverted? It checks while the evidence exists: GitHub deletes old CI runs, so a claim that is
not checked when the PR is made often cannot be checked at all later.

> **Status: beta (0.5).** The engine, the coding pack, the CLI and the GitHub Action are
> tested (1,000+ tests) and have run live on a sandbox repository with 30 agent pull requests.
> Interfaces may change before 1.0.

## Try it

Requires [uv](https://docs.astral.sh/uv/). Nothing to install or configure:

```bash
uvx second-source check https://github.com/OWNER/REPO/pull/123
```

A GitHub token is picked up automatically from `GITHUB_TOKEN`, `GH_TOKEN` or a logged-in
GitHub CLI. Without one, the public API allows about 10 PR checks per hour.

Example output:

```text
Second Source · Octo/App#7 · https://github.com/Octo/App/pull/7
Agent: codex (detected by branch_prefix: codex/)
Claims: 1 unverifiable, 2 pending, 3 verified

? unverifiable Deployed to staging (low confidence)
    said in comment: "Deployed to staging."
    why: no deployment of this commit was found
… pending      Fixes #12
    said in body: "Fixes #12"
    why: issue closed; watching for a reopen
✔ verified     Tests added
    said in body: "Added unit tests for empty input"
    why: test files changed
✔ verified     Tests pass (low confidence)
    said in body: "- ✅ `pytest -q`"
    why: every matching CI job passed
```

| Option | What it does |
|---|---|
| `--json` | Machine-readable output (versioned schema) |
| `--anonymous` | Never use a token, even if one is available |
| `--no-cache` | Skip the on-disk response cache |
| `--no-color` | Plain text (colour is also off when `NO_COLOR` is set) |

Exit codes: `0` nothing contradicted, `1` at least one claim contradicted, `2` could not check.

## Use it in your repository (GitHub Action)

One command writes the workflow; commit it and every PR opened by a coding agent gets a
**Second Source** check next to your CI:

```bash
uvx second-source init
```

The generated `.github/workflows/second-source.yml`:

- checks agent PRs when they are opened or updated, waits a few minutes for CI, and updates the
  check when your CI workflows finish (it reads their names from `.github/workflows`);
- ends every check with **evidence at a glance**: CI on the head commit, what the change
  touched (tests, CI configuration) and merge or revert state, even when the PR claims nothing;
- re-checks recent agent PRs daily, for durability (reverts, reopened issues);
- understands `/second-source recheck` and `/second-source dispute <reason>` in PR comments
  (from the PR author or people with write access).

<details>
<summary>Or copy the workflow by hand (replace <code>"CI"</code> with your CI workflow names)</summary>

```yaml
# Second Source: checks the claims coding agents make in their pull requests.
# Generated by `second-source init`. Docs: https://github.com/Rarebuffalo/second-source
#
# Safe with pull_request_target: Second Source reads the PR through the API only and never
# checks out or runs its code. Do not add an actions/checkout step to this workflow.
name: Second Source

on:
  pull_request_target:
    types: [opened, edited, synchronize, reopened, ready_for_review, closed]
  # Re-check when CI finishes, so verdicts no longer wait on it.
  workflow_run:
    workflows: ["CI"]
    types: [completed]
  issue_comment:
    types: [created]
  schedule:
    - cron: "17 6 * * *"  # daily: durability (reverts, reopened issues) and pending claims
  workflow_dispatch:

permissions:
  checks: write
  contents: read
  pull-requests: write  # to label a disputed PR (GitHub requires it for PR labels)
  issues: write
  actions: read

concurrency:
  group: second-source-${{ (github.event_name == 'issue_comment' && contains(github.event.comment.body, '/second-source dispute') && github.run_id) || github.event.issue.number || github.event.pull_request.number || github.event.workflow_run.pull_requests[0].number || github.run_id }}
  cancel-in-progress: false

jobs:
  # The job id is its check-run name; checks ignore "second-source" as CI evidence.
  second-source:
    # Comments only matter when they hold a /second-source command on a pull request.
    if: >-
      github.event_name != 'issue_comment' ||
      (github.event.issue.pull_request && contains(github.event.comment.body, '/second-source'))
    runs-on: ubuntu-latest
    timeout-minutes: 75
    steps:
      - uses: Rarebuffalo/second-source@v0
```

</details>

By default the check is advice: a contradicted claim makes it *neutral*, never failing. Set
`fail-on-contradiction: "true"` to make it block merges. Other inputs: `wait-minutes`
(default 10), `only-agents`, `sweep-days`, and `ignore-claims` to switch off claim types you
find noisy (for example `LINT_OK, DOCS_UPDATED`). It needs no server and no secrets, and never
checks out the PR's code. Design: [docs/action.md](docs/action.md). To run exactly the code
you reviewed, pin a commit SHA instead of `@v0`; see [SECURITY.md](SECURITY.md).

### What it costs

- **Money:** nothing. It is open source and runs in your own GitHub Actions.
- **Actions minutes:** free on public repositories. On private ones each run uses 15–45
  seconds plus up to `wait-minutes` (default 10) waiting for CI; set `wait-minutes: 0` there
  and the check updates when CI finishes instead.
- **API requests:** about 10–15 per PR check from the workflow's own `GITHUB_TOKEN`, whose
  limit is 1,000 an hour per repository. PR text cannot raise this without bound (at most 20
  issue references and 8 commits are looked up), and the daily sweep stops while 200 requests
  remain for PR events.

### When it is wrong

The default never blocks a merge, so a wrong verdict costs a reader's attention, not a
release. If a verdict looks wrong:

1. Comment `/second-source dispute <why>` on the PR. The check is marked *disputed* at once, so
   nobody else relies on it.
2. Report it with the [wrong-verdict form](https://github.com/Rarebuffalo/second-source/issues/new?template=wrong_verdict.yml)
   (for a private repository, describe it without the link). We aim to acknowledge reports
   within 5 working days; a rule fix ships as a patch release and moves the `@v0` tag.
3. If a claim type keeps being wrong for your repository, switch it off with `ignore-claims`.

## What it checks

| Claim | Example wording | Checked against |
|---|---|---|
| Tests pass | "All tests pass", "✅ `pytest`" | CI test jobs on the commit the claim refers to |
| Build succeeds | "Build succeeds", "`cargo build` ✅" | CI build jobs on that commit |
| Lint passes | "Lint passes", "no ESLint warnings" | CI lint, format and type-check jobs |
| Tests added | "Added unit tests for the parser" | Test files changed in the PR (never contradicted: tests can live in code files) |
| Docs updated | "Updated the README" | Documentation files changed in the PR (never contradicted: docs can live in code) |
| Fixes an issue | "Fixes #123", "Closes owner/repo#45" | Issue closed by the merge, and still closed later |
| Deployed | "Deployed to staging" | GitHub deployment records |
| Merge holds (implicit) | every merged agent PR | No revert of the merge within 30 days |

Each claim gets one verdict:

- **verified**: the evidence agrees.
- **contradicted**: the evidence disagrees, for example the test job failed on that commit.
- **pending**: too early to tell (CI still running, or inside the durability window).
- **unverifiable**: there is no evidence either way.

**Missing or unavailable evidence is never reported as contradicted.** A claim the text says
ran *locally* ("tests pass locally") is not contradicted by failing CI either; it gets its own
reason, `CI_FAILED_LOCAL_CLAIM`, because local and CI environments differ.

Claims are found with deterministic rules, and no AI model reads the PR text or decides a
verdict, so results are reproducible and instructions written into a PR cannot steer them.
Each claim is marked **high** or **low confidence** depending on whether a rule with measured
high precision found it.

## How accurate is it?

Claim extraction is measured on a public golden set: 402 real agent pull requests from the
[AIDev](https://huggingface.co/datasets/hao-li/AIDev) dataset, 67 per agent, each labelled by
two independent labellers (96% exact agreement). **Both labellers were AI model sessions**,
each given only the labelling guide and the PR text; because they are the same kind of model,
their agreement overstates independence, and a human audit of a sample is planned. Half the set
is used to tune rules; the other half is scored only to report.

On the held-out half, precision is 1.00 for issue references and lint claims and 0.88 for
high-confidence "tests pass" claims, below our 0.95 target. Full numbers, the labelling guide
and the method: [tests/packs/coding/golden/real/](tests/packs/coding/golden/real/README.md).
Until every claim type meets the target, we treat a "contradicted" verdict as a strong signal
that a person should confirm, not as proof.

## What the benchmark found

On 1,175 merged agent PRs from AIDev (run 2): of 385 PRs we could still check, 2 had a claim
GitHub's record proves false. That is a floor, not a rate. The bigger finding: **the evidence
expires.** Every "tests pass" claim we could verify was under a year old; for 42 of the 43
older ones, GitHub had already deleted the CI runs. Claims need checking when the PR is made,
which is what the [GitHub Action](#use-it-in-your-repository-github-action) does.

Caveats matter here: 185 of the 385 PRs were checked only on claim types that never
contradict, a blind audit judged more claims false than the rules count, and only merged PRs
were sampled. Numbers, caveats and the comparison with related work:
[docs/benchmark.md](docs/benchmark.md#11-run-2-findings).

## How it works

```text
pull request ──> detect agent ──> extract claims ──> fetch only the evidence those claims need
             ──> run checks (YAML + CEL, pure and replayable) ──> verdicts ──> report
```

- **Domain-neutral core.** The engine knows nothing about code. Claims, evidence and checks
  are generic; the coding pack adds the coding-specific parts. A customer-support fixture pack
  in the tests keeps the core honest.
- **Checks are data.** Each check is a small YAML file with [CEL](https://cel.dev)
  expressions, so its logic is readable and reviewable
  ([example](src/second_source/packs/coding/checks/ci_result.yaml)).
- **Replayable.** Every check records a hash of its exact inputs; the same inputs always give
  the same verdict.

More: [architecture](docs/ARCHITECTURE.md), [coding pack](docs/packs/coding.md),
[GitHub source](docs/sources/github.md), [benchmark method](docs/benchmark.md).

## Privacy and security

- The CLI talks only to the GitHub API. Nothing is sent to us or anyone else.
- Tokens are never printed, logged or written to the cache, and the cache never stores code.
- PR code is never checked out or run, which is why the Action can safely use
  `pull_request_target`.
- Report vulnerabilities privately: see [SECURITY.md](SECURITY.md).

## Roadmap

- **Released: 0.5.0 (beta).** The Action as `@v0`, the CLI on PyPI (`uvx second-source`), and
  run 2's aggregate results as [open data](docs/benchmark-data/run2/README.md).
- **Evidence that outlives GitHub's retention.** The Action keeps a compact, tamper-evident
  record of the evidence behind each verdict, with a `replay` command, so a verdict can still be
  checked after GitHub deletes the CI runs.
- **A benchmark checked at PR time.** Run 3 checks recent agent PRs while their evidence still
  exists.
- **Precision.** Every claim type shown as a finding at 0.95 or better on fresh held-out data.
- **More domains.** The same core for customer-support, voice and other agents, where their
  systems keep a record that can be read.
