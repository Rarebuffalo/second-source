# GitHub Action reference

The Action adds a check named "Second Source" to every pull request opened by a coding agent.
The check lists the agent's claims, the verdict on each and the evidence behind it, and it is
updated as CI finishes and, after the merge, while durability claims are watched. It runs in your
own GitHub Actions with the workflow's `GITHUB_TOKEN`: there is no server, account or secret.

On the GitHub Marketplace it is listed as
[Second Source Claim Check](https://github.com/marketplace/actions/second-source-claim-check).

## Workflow

`uvx second-source init` writes this file to `.github/workflows/second-source.yml`, with the
names of your CI workflows filled in under `workflow_run`:

```yaml
# Second Source: checks the claims coding agents make in their pull requests.
# Generated by `second-source init`. Docs: https://github.com/Rarebuffalo/second-source
#
# Safe with pull_request_target: Second Source reads the PR through the API only and never
# checks out or runs its code. Do not add an actions/checkout step to this workflow.
name: Second Source

on:
  pull_request_target:
    types: [opened, edited, synchronize, reopened, ready_for_review, closed]
  # Re-check when CI finishes, so verdicts no longer wait on it.
  workflow_run:
    workflows: ["CI"]
    types: [completed]
  issue_comment:
    types: [created]
  schedule:
    - cron: "17 6 * * *"  # daily: durability (reverts, reopened issues) and pending claims
  workflow_dispatch:

permissions:
  checks: write
  contents: read
  pull-requests: write  # to label a disputed PR (GitHub requires it for PR labels)
  issues: write
  actions: read

concurrency:
  group: second-source-${{ (github.event_name == 'issue_comment' && contains(github.event.comment.body, '/second-source dispute') && github.run_id) || github.event.issue.number || github.event.pull_request.number || github.event.workflow_run.pull_requests[0].number || github.run_id }}
  cancel-in-progress: false

jobs:
  # The job id is its check-run name; checks ignore "second-source" as CI evidence.
  second-source:
    # Comments only matter when they hold a /second-source command on a pull request.
    if: >-
      github.event_name != 'issue_comment' ||
      (github.event.issue.pull_request && contains(github.event.comment.body, '/second-source'))
    runs-on: ubuntu-latest
    timeout-minutes: 75
    steps:
      - uses: Rarebuffalo/second-source@v0
```

Do not add an `actions/checkout` step. The Action reads the pull request through the API and
never needs its code; see [Why `pull_request_target` is safe here](#why-pull_request_target-is-safe-here).

## Inputs

| Input | Default | Description |
|---|---|---|
| `github-token` | `${{ github.token }}` | Token used to read the pull request and write the check run. |
| `wait-minutes` | `10` | How long a run waits for CI before publishing (0 to 60). Use `0` on private repositories to save Actions minutes; the check then updates when CI finishes. |
| `only-agents` | `true` | Skip pull requests with no detected coding agent, so human pull requests are never checked. |
| `fail-on-contradiction` | `false` | Make a contradicted claim fail the check. By default it is advice and never blocks a merge. |
| `sweep-days` | `30` | How far back, in days, the daily run re-checks agent pull requests. |
| `ignore-claims` | `""` | Claim types to switch off, comma-separated: `TESTS_PASS`, `BUILD_OK`, `LINT_OK`, `TESTS_ADDED`, `DOCS_UPDATED`, `FIXES_ISSUE`, `DEPLOYED`. They are neither checked nor shown. An unknown name fails the run. |

The Action has no outputs; its result is the check run and the job summary.

## Permissions

| Permission | Why |
|---|---|
| `checks: write` | Create and update the "Second Source" check run. |
| `contents: read` | Read commits and the files the pull request changed. |
| `pull-requests: write` | Add the `second-source: disputed` label; GitHub requires this permission to label pull requests. |
| `issues: write` | Post the reply to `/second-source dispute`. |
| `actions: read` | Read workflow runs, to know whether CI on a commit is still coming. |

## Events

| Event | What the Action does |
|---|---|
| `pull_request_target` | Checks the pull request when it is opened, edited, updated, reopened, marked ready or closed. If CI has not finished, it waits up to `wait-minutes`. |
| `workflow_run` (completed) | Re-checks the pull requests whose head commit the finished CI run built. |
| `issue_comment` | Runs a `/second-source` command; other comments are ignored. |
| `schedule` (daily) | Re-checks agent pull requests updated in the last `sweep-days`, for durability claims and anything still pending. |
| `workflow_dispatch` | Runs the same sweep by hand. |

A CI workflow added after `init` is not listed under `workflow_run`; add its name there, or the
check updates only on the next pull request event or daily run.

## The check run

The check run's title and conclusion summarise the verdicts:

| Verdicts | Conclusion | Example title |
|---|---|---|
| A high-confidence claim is contradicted | `neutral`, or `failure` with `fail-on-contradiction: true` | 1 claim contradicted |
| A deciding claim is still waiting for CI | stays in progress | Waiting for CI |
| CI passed, but the same pull request skipped tests, weakened its test command or lowered a coverage gate | `neutral`, never `failure` | 1 claim not verified: this PR skips tests |
| A claim is unverifiable because CI failed where its wording leaves room (a local run, part of the suite, one of two commits) | `neutral` | 1 verified, 1 unverifiable (a CI job failed) |
| No claims | `neutral` | No claims found |
| Otherwise | `success` | 2 verified, 1 pending |

Low-confidence claims are shown but never change the conclusion. Cautions, such as a change to
CI configuration, appear next to a claim's result and never change the conclusion either.

The summary has a table of claims, then "Evidence at a glance": CI on the head commit, what the
change touched (files, tests, CI configuration, removed tests, lint suppressions) and the merge
and revert state. [Claims and verdicts](claims.md) explains every result and reason.

## Waiting for CI

A claim such as "tests pass" can only be judged once CI finishes. A run waits, polling with
backoff, while a claim can still be decided: a matching job is running, a GitHub Actions
workflow on the commit is unfinished (queued, waiting on `needs:` jobs, or held for approval, as
Copilot and fork pull requests are until someone approves the run), or other CI on the commit is
still running. A commit whose CI has finished without a matching job is decided at once.

A claim waits at most 6 hours from the commit or from when its CI was triggered. If a workflow
is still unfinished then, passing jobs do not verify the claim. While anything is waiting, the
check stays in progress with the current table.

## Commands

The pull request's author and people with write access can comment:

| Command | Effect |
|---|---|
| `/second-source recheck` | Check the pull request again now. |
| `/second-source dispute <reason>` | Mark the pull request as disputed: the Action adds the `second-source: disputed` label, the check says so, and the Action replies once with a link to the wrong-verdict form. The reply never repeats the comment. |

Other comments, and commands from anyone else, are ignored.

## Versioning and pinning

`@v0` follows the latest 0.x release, so fixes arrive without editing the workflow. To run only
code you have reviewed, pin a full commit SHA and update it deliberately:

```yaml
- uses: Rarebuffalo/second-source@852e2a6ed146f4d73c774f5bd9a1a67aa3e86e3b  # v0.5.1
```

Release notes are in the [changelog](../CHANGELOG.md).

## Private repositories and forks

On private repositories each run uses Actions minutes: 15 to 45 seconds, plus up to
`wait-minutes` while waiting for CI. Setting `wait-minutes: 0` avoids the waiting; the
`workflow_run` event updates the check when CI finishes.

Pull requests from forks are checked like any other. On public repositories GitHub gives fork
pull requests a read-only token, so they cannot change the check run.

## Cost and limits

Each check uses about 10 to 15 GitHub API requests from the workflow's `GITHUB_TOKEN`, whose
limit is 1,000 an hour per repository. To protect that quota from crafted pull request text, at
most 20 issue references, 8 commits with CI claims and 4 with deploy claims are looked up per
pull request, the body's first; claims past that are reported unverifiable. The daily run stops
while 200 requests remain, and starts at a different pull request each day.

Runs on one pull request share a queue, so a burst of events or `recheck` comments costs one
run; a dispute has its own queue and is never dropped. An older result never replaces a newer
one. A job times out after 75 minutes.

## Why `pull_request_target` is safe here

With `pull_request`, fork pull requests get a read-only token and cannot create check runs, so
the workflow uses `pull_request_target`, which runs with the base repository's token. That event
is dangerous for workflows that check out and run pull request code. Second Source never does:
it installs itself from the Action's own pinned, hash-locked dependencies, reads the pull
request only through the API, treats all of its text as untrusted, and never imports from the
workspace. The [security model](security-model.md) covers this in detail.
